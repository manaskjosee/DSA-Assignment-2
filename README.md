# Song ID Hash Table — Division Method, Collisions & Search Performance

A DSA project for a music application that indexes song IDs using a hash
table built with the **Division Method**, and compares hashed lookup
against plain **linear search**.

## Part (a): Building the hash table (Division Method)

**Hash function:** `h(k) = k mod m`, with table size **m = 10**.
**Collision resolution:** separate chaining (each bucket holds a list).

Table size 10 was chosen deliberately (see the design note at the end of
Part c) — it's a very natural first choice for 8 keys, and it also happens
to expose a classic hashing pitfall that's worth understanding.

Insertions in the given order, with the table shown after **every**
insertion:

| Step | Key | h(key) = key mod 10 | Bucket after insert | Collision? |
|---|---|---|---|---|
| 1 | 105 | 5 | `[5] = [105]` | No |
| 2 | 210 | 0 | `[0] = [210]` | No |
| 3 | 315 | 5 | `[5] = [105, 315]` | **Yes** |
| 4 | 420 | 0 | `[0] = [210, 420]` | **Yes** |
| 5 | 525 | 5 | `[5] = [105, 315, 525]` | **Yes** |
| 6 | 630 | 0 | `[0] = [210, 420, 630]` | **Yes** |
| 7 | 735 | 5 | `[5] = [105, 315, 525, 735]` | **Yes** |
| 8 | 840 | 0 | `[0] = [210, 420, 630, 840]` | **Yes** |

Final table:

```
Index  Bucket contents (chain)                Chain length
------------------------------------------------------------
0      [210, 420, 630, 840]                   4
1      -- empty --                            0
2      -- empty --                            0
3      -- empty --                            0
4      -- empty --                            0
5      [105, 315, 525, 735]                   4
6      -- empty --                            0

```

**Collision summary:** 8 insertions → **6 collisions**, only **2 of 10
buckets used**, longest chain = 4.

## Part (b): Search — Hashing vs. Linear Search

The assignment didn't specify which IDs to search, so I searched a
representative mix: two present IDs, one best-case present ID, one absent
ID, and one absent ID that still collides on insert. (Swap in whatever IDs
your assignment specifies — `main.py`'s `SEARCH_IDS` list is the only line
you'd need to change.)

| Key | Hashing: found? | **Hash comparisons** | Linear search: found? | **Linear comparisons** |
|---|---|---|---|---|
| 630 | Yes | **3** | Yes | 6 |
| 735 | Yes | **4** | Yes | 7 |
| 105 | Yes | **1** | Yes | 1 |
| 999 | No | **0** | No | 8 |
| 615 | No | **4** | No | 8 |

**What "comparisons" means here:**
- *Hashing*: one hash computation (O(1), not counted as a "comparison")
  plus one key-comparison per element walked in that bucket's chain.
- *Linear search*: one key-comparison per element scanned in the original
  array `[105, 210, 315, 420, 525, 630, 735, 840]`, left to right, until
  found or the array is exhausted.

**Observation:** hashing wins every single case above — even its *worst*
case here (615, 4 comparisons, caused by a full chain) beats linear
search's *best* miss case (999, 8 comparisons). Only when the target is
the very first element checked (105) do the two methods tie.

## Part (c): Effect of collisions, load factor, and suitability

### Load factor

```
α = n / m = 8 / 10 = 0.8
```

### Theoretical vs. observed complexity

| | Theoretical (avg case, uniform hashing) | Observed here |
|---|---|---|
| Hashing (chaining) | O(1 + α) ≈ **1.8** comparisons/search | **2.4** avg comparisons over the 5 test searches |
| Linear search | O(n) ≈ **n = 8** comparisons worst case, ~n/2 average | **6.0** avg comparisons over the same 5 searches |

Hashing still comfortably outperforms linear search in absolute terms.
But notice the *gap between theory and reality* for hashing: the textbook
formula O(1+α) assumes keys are spread **uniformly** across buckets. Here
they are not — only 2 of the 10 buckets are used at all, so the chains
that do exist are much longer (up to 4) than the "average" the formula
predicts, and worst-case hashed search degrades toward the same O(n)
behaviour as linear search (see key `615`: 4 comparisons, close to what
a small linear scan would cost).

### Why did this happen? (the real insight)

All 8 song IDs are multiples of 105, and `105 = 3 × 5 × 7`. The table
size chosen was `m = 10 = 2 × 5`. Because 105 and 10 share the common
factor **5**, every key's residue mod 10 can only ever be `0` or `5`
(consecutive keys' hash values simply alternate between the two). No
matter how many more song IDs you inserted that follow this `+105`
pattern, they would *never* land anywhere except buckets 0 and 5. This is
a textbook example of why the division method's quality depends heavily
on the relationship between the table size and the structure of the key
set — a "reasonable-looking" load factor of 0.8 can still hide terrible
clustering.

**Fix:** choose `m` as a prime that shares no factors with the data's
pattern. Re-running the exact same 8 keys with `m = 11` (prime, doesn't
divide 105) gives:

```
Index  Bucket contents                Chain length
0      -- empty --                    0
1      [210]                          1
2      [420]                          1
3      [630]                          1
4      [840]                          1
5      -- empty --                    0
6      [105]                          1
7      [315]                          1
8      [525]                          1
9      [735]                          1
10     -- empty --                    0
```

**Zero collisions**, every search now costs exactly 1 comparison — true
O(1). Load factor is 8/11 ≈ 0.73, similar to before, which proves the
point: load factor alone doesn't determine performance — the *hash
function's fit to the data* does.

### Is hashing suitable for this application?

**Yes — hashing is suitable, and clearly better than linear search, but
table size must be chosen carefully.** For a music app indexing song IDs:

- Song ID lookup is a classic "point lookup by exact key" access pattern
  — exactly what hashing is built for (O(1) average vs. O(n) for linear
  search), which matters a lot once the catalogue has millions of songs
  rather than 8.
- The catalogue will keep growing, so the table should be **resized
  (rehashed) as the load factor climbs past ~0.7**, and future table
  sizes should be chosen as **primes** to avoid the exact clustering
  problem demonstrated above — especially important here since song IDs
  plausibly follow structured/patterned schemes (sequential blocks,
  multiples tied to an album or artist ID, etc.), not random values.
- With that one fix (prime table size), this data set goes from 6
  collisions / longest chain 4, to 0 collisions / every lookup O(1) —
  hashing becomes strictly superior to linear search in every case
  instead of merely "usually better."

## Complexity reference

| Operation | Linear Search | Hashing (chaining), average | Hashing (chaining), worst case |
|---|---|---|---|
| Search | O(n) | O(1 + α) | O(n) (all keys collide) |
| Insert | O(1) (append) / O(n) (if checking duplicates) | O(1) average | O(n) worst case |
